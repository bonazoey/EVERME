# 백엔드 코드·주석 컨벤션

이 문서는 `backend/` 하위 코드를 새로 작성하거나 수정할 때 적용한다. 변경하는 파일의 기존 형식을 우선 존중하고, 요청과 관계없는 파일까지 일괄 정리하지 않는다.

## 패키지와 역할

- Spring MVC의 기본 흐름은 Controller → Service → Dao로 구성한다.
- Controller는 HTTP 요청·응답과 입력 검증, Service는 업무 처리·트랜잭션, Dao는 DB 접근을 담당한다.
- 일반 백엔드는 `com.example.everme` 하위의 `controller`, `service`, `dao`, `dto` 패키지에 배치한다.
- Clone Lab은 `com.example.everme.lab` 내부에서 같은 계층을 구분한다. 실험 코드와 API의 `clone-lab` 프로필 조건을 유지한다.
- 클래스명은 `XxxController`, `XxxService`, `XxxDao`를 사용한다. MyBatis 매퍼 인터페이스는 `XxxMapper`로 구분한다.
- 설정·검증·카탈로그 등 별도 책임의 클래스는 역할에 맞는 이름을 사용한다. 모든 클래스를 억지로 Service 또는 Dao로 명명하지 않는다.

## Java 작성 방식

- Java 21과 Spring Boot의 현재 프로젝트 설정을 따른다. 파일 인코딩은 UTF-8을 사용한다.
- 클래스·인터페이스는 PascalCase, 메소드·변수는 camelCase, 상수는 UPPER_SNAKE_CASE로 작성한다.
- 의존성은 생성자로 주입하고, 변경할 필요가 없는 의존성 필드는 `final`로 선언한다.
- 클래스 내부는 필드 → 생성자 → 기능별 메소드 순서로 배치한다.
- 들여쓰기·중괄호·줄바꿈은 수정하는 파일의 기존 스타일을 따른다. 새 일반 Java 클래스는 Lab의 기존 2칸 들여쓰기를 기준으로 하되, 기존 4칸 파일은 그 형식을 유지한다.
- import는 명시적으로 작성하고 사용하지 않는 import를 제거한다. 기존 파일의 import 그룹을 따른다.
- 메소드에는 역할을 드러내는 이름을 사용하고, 복잡한 조건·반복·단계 처리는 이해할 수 있는 단위로 나눈다.
- 예외·응답·트랜잭션 처리는 해당 기능의 기존 계약을 따른다. 컨벤션 정리만으로 동작이나 API 계약을 변경하지 않는다.

## 주석

- 설명 주석은 한국어로 작성한다. 클래스명·API명·필드명 등 기술 식별자는 원래 표기를 유지한다.
- 필드와 생성자 구역은 기존 Lab 형식을 사용한다.

```java
// ##### 필드 #####
private final LabService labService;

// ##### 생성자 #####
public LabController(LabService labService) {
  this.labService = labService;
}
```

- 엔드포인트와 주요 처리 메소드 위에는 수행하는 기능을 구체적으로 적는다.

```java
// ##### 분석 프로필을 조회하는 메소드 #####
```

- 짧은 접근자나 자명한 코드에 같은 내용을 반복하는 주석을 강제로 추가하지 않는다.
- 복잡한 로직은 문법을 설명하기보다 처리 이유·순서·제약·실패 시 동작을 설명한다.
- 클래스 책임과 상수의 의미처럼 IDE에서 확인할 설명은 `/** ... */` 형식의 Javadoc을 사용한다.
- 수정 시 주석도 실제 동작과 일치시킨다. 아직 구현하지 않은 설계를 구현된 것처럼 설명하지 않는다.

## LLM 프롬프트와 카탈로그

- Clone Lab의 고정 프롬프트는 `lab/prompt/LabPrompts.java`에서 관리한다. 서비스 안에 고정 지침 문자열을 분산하지 않는다.
- 각 프롬프트 상수 위에는 사용 단계와 목적을 설명하는 한국어 Javadoc을 작성한다.
- 프롬프트는 Java 텍스트 블록(`"""`)으로 표현한다. 줄마다 문자열을 `+`로 연결하지 않는다.
- 공통 지침 삽입은 텍스트 블록과 `.formatted(...)`를 사용한다. 줄바꿈은 문장의 의미를 기준으로 나눈다.
- 프롬프트 지침, 요소 카탈로그, 출력 JSON Schema의 책임을 구분한다. 카탈로그는 `LabCatalog`, 출력 Schema는 `LabSchemas`에서 관리한다.
- 분석용 축소 카탈로그는 공통 앵커를 `anchorDefinitions`에 한 번 정의하고, 각 요소의 `anchorRef`로 참조한다.
- 축소 과정에서 140개 요소의 의미·점수 해석·예시·경계를 잃지 않는다. 화면·내보내기용 전체 카탈로그와 분석용 입력을 구분한다.
- LLM 요청·응답 로그는 기존 `SimpleLoggerAdvisor`와 포매터를 사용한다. 업무 단계·처리 시간 로그는 SLF4J를 사용한다.

## 검증과 변경 범위

- 주석만 수정한 경우 프롬프트 본문이나 실행 로직을 함께 변경하지 않는다.
- 코드 변경은 관련 테스트로 검증한다. 카탈로그 구조 변경 시 전체 요소 포함 여부와 참조 복원 시 기존 의미가 유지되는지 확인한다.
- 실제 LLM 호출은 비용이 발생하므로 자동 검증은 기존 모의 모델 테스트를 우선 사용한다. 실제 호출을 하지 않았다면 그 한계를 결과에 명시한다.
- DBML·설계 문서 수정과 실행 DB·마이그레이션·Java 구현 변경은 구분한다. 설계 문서를 수정했다는 이유만으로 실제 DB에 적용하지 않는다.

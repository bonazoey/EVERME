## 1. 오늘 작업의 목표

실서비스 전체를 구현하기보다 다음 핵심 과정을 간단한 실험 화면에서 확인하는 것이 목표다.

```text
사용자 대화
  → LLM이 사용자 발언 분석
  → 7개 영역·140개 요소의 수치를 DB에 누적 반영

  → 정보이용자가 클론과 대화하며 결과 검증
```

확인하려는 것은 단순한 답변 생성 여부가 아니다. 대화 원문이 보존되는지, 근거에 맞게 수치가 갱신되는지, 기존 관찰이 새 관찰 한 번에 과도하게 흔들리지 않는지, 클론이 실제 기억과 성향 추정을 구분하는지를 확인한다.

## 3. 대화 생성이 느린 문제

### 문제와 고민

10쌍의 테스트 대화를 만드는 데 약 20초가 걸렸다. ChatGPT 화면에서 빠르게 작성되는 체감과 비교해 API 호출이 오래 걸리는 이유를 확인하려 했다.

이전 대화에서는 입력 약 32,000토큰·생성 약 40초라는 검증 기록이 언급됐다. 이는 이전 측정치이며, 오늘 변경 후 다시 측정한 성능이 아니다.

### 확인한 구조

- 사용자·AI 발언을 20번 개별 호출하는 것이 아니라 한 번 호출해 10쌍을 생성한다.
- 대화 생성에 분석용 140개 명세와 정답 점수표를 함께 주는 것은 입력 비용과 처리 부담을 늘린다.
- 입력을 줄여도 출력 토큰 생성, 모델 추론, 네트워크와 공급자 대기 시간이 남는다.
- 프레임워크를 Spring AI로 바꿨다는 사실만으로 생성 속도가 빨라진다고 보장할 수 없다.

### 반영

- 테스트 대화 생성에는 주제와 최근 4쌍을 전달한다.
- 인물의 배경·정답 점수표는 생성·분석·클론 답변에 전달하지 않고 비교 평가용으로 분리했다.
- 생성 추론 강도는 `low`, 분석·요약은 `medium`, 답변은 미지정으로 설정했다.
- 분석 입력은 전체 화면용 카탈로그 대신 분석에 필요한 정의·앵커·경계·예시 중심으로 축소했다.
- 고정 지침·카탈로그를 앞에 두고 가변 원문·요약을 뒤에 배치한다. 캐시 적중 자체를 보장하지는 않는다.
- 시간·토큰·캐시·재시도 집계를 확인할 수 있게 했다.

### 테스트 대화의 AI 역할

- 사용자가 이야기를 주도한다.
- AI는 공감·경청·맞장구를 중심으로 반응한다.
- 필요하면 연결되는 열린 질문을 최대 하나 덧붙인다.
- 매번 질문하거나 새 주제·조언·해결책을 먼저 제시하지 않는다.
- 사용자에게서 나오지 않은 경험·감정을 단정하거나 점수 평가를 대화에 드러내지 않는다.

## 4. 대화 입력·주제·분석 문맥 개선

### 반영한 화면과 동작

- 같은 주제에 대화 10쌍을 추가하는 버튼을 제공한다.
- 대화 내역 아래 직접 입력창을 제공해 실제 사용자가 발언을 입력할 수 있다.
- 주제가 없으면 첫 10쌍에서 주제를 추론해 적용한다.
- 생성·분석·저장을 분리한다. 생성만 해도 분석·프로필 저장이 자동 실행되는 것은 아니다.

### 분석과 요약의 경계

- 새 관찰 근거는 분석 대상 구간의 실제 사용자 발언이다.
- 이전 대화의 요약은 문맥 보조이며 새 점수·새 기억의 출처로 삼지 않는다.
- 같은 대화에서 앞선 10쌍 단위 요약을 최근 최대 5개 붙인다.
- 다른 주제의 대화 요약은 가져오지 않는다.
- 파이프라인 구간의 요약은 DB의 구간 JSON에 보존해 재사용한다.

분석하지 않은 발언을 단순히 요약에만 넣고 버리는 방식으로 처리해서는 안 된다. 현재 자동 실행은 고정된 10쌍 구간을 순서대로 분석·저장하며, 각 구간의 원문 ID를 고정해 뒤쪽 대화가 섞이지 않게 한다.

## 5. 분석 점수와 누적 반영 방식

### 고민

기존 값이 40이고 이번 관찰이 60이라고 무조건 평균 50을 저장하는 것은 적절하지 않다. 기존 40이 오랜 기간의 많은 관찰로 형성됐다면 새 관찰 한 번과 동일한 비중을 주기 어렵다.

반대로 누적 가중치를 무제한으로 늘리면 오래된 점수가 너무 강해져 실제 변화가 반영되지 않을 수 있다.

### 현재 규칙

- 7개 영역 × 20개 요소 = 140개 요소다.
- 모든 점수는 `0~100`이며 요소별 독립 점수다. 합계 100 제약은 없다.
- `50`은 중간 성향, `NULL`은 근거 부족이다.
- 근거 부족을 DB에서 일괄 50으로 채우지 않는다. 화면의 초기 기준값 50과 실제 저장값은 구분한다.
- 내향·외향처럼 같은 축은 하나의 요소로 표현한다.
- 근거 강도는 `1~3`이다.
- 요소마다 가중치 상한 `10 / 20 / 40`을 명시한다.
- 상한은 초기 실험 정책이며 검증된 심리학적 변화 속도나 중요도를 의미하지 않는다.

```text
C = 요소별 가중치 상한
W = 기존 점수가 NULL이면 0, 아니면 min(기존 가중치, C)
s = 새 근거 강도

새 점수 = 최초 관찰이면 이번 관찰값
          아니면 (기존 점수 × W + 관찰값 × s) / (W + s)

저장 가중치 = min(W + s, C)
```

기존 점수 40, 가중치가 해당 상한에 도달한 상태에서 관찰 60·강도 2를 반영하면:

| 상한 | 결과 | 의미 |
| ---: | ---: | --- |
| 10 | 43.33 | 최근 관찰을 상대적으로 빠르게 반영 |
| 20 | 41.82 | 중간 속도 |
| 40 | 40.95 | 기존 관찰을 더 오래 보존 |

소수 둘째 자리 `HALF_UP` 반올림을 적용한다. 기존 가중치가 새 상한보다 높으면 계산 시 제한하고, 새 상한이 높아졌다는 이유로 기존 가중치를 부풀리지 않는다. 관찰이 없는 요소는 유지한다.

### 병합 LLM 호출 제거

이전에는 LLM이 가중평균을 계산하고 서버가 같은 공식을 다시 계산해 비교했다. 이 구조는 같은 계산을 반복하면서 LLM의 산술·반올림 오류로 저장이 실패할 가능성을 만들었다.

현재는 `LabValidation`에서 `BigDecimal`로 직접 계산한다. 분석 LLM은 관찰값·근거·강도 판단을 담당하고, 수치 병합은 서버가 담당한다. 병합 모델 설정과 병합 요청 Schema는 제거했다. 과거 저장 결과의 `mergeMetrics`는 기존 데이터로 읽을 수 있게 유지한다.

## 6. 1000쌍 자동 실행 구조 변경

### 비교한 두 접근

| 접근 | 특성 |
| --- | --- |
| 한 대화에 1000쌍 생성 후 전체 분석·한 번 저장 | 중간 결과가 늦게 반영되고 중간 장애 시 진행 확인이 어려움 |
| 여러 배치를 동시에 생성·분석 후 순차 저장 | 처리량은 높일 수 있으나 한 대화를 자연스럽게 잇는 요구와 다름 |

최종 선택은 **하나의 대화에서 생성 작업 1개와 분석·저장 작업 1개를 병행**하는 방식이다.

```text
생성:       1~10 → 11~20 → 21~30 → …
분석·저장:         1~10 → 11~20 → 21~30 → …
```

### 반영

- 동일한 `batchId`와 주제로 총 1000쌍을 이어 생성한다.
- 10쌍씩 100개 구간을 만든다.
- 생성끼리는 병렬 실행하지 않고, 분석끼리도 병렬 실행하지 않는다.
- 생성 예약을 포함한 미저장 구간은 최대 2개, 20쌍이다.
- 분석이 밀리면 생성을 대기시키는 역압을 적용한다.
- 각 구간은 7개 분야를 한 번의 분석 호출로 처리한다.
- 구간 순서대로 저장하며, 관찰이 없는 구간도 완료로 기록한다.
- 정상적인 새 실행은 저장 100회와 프로필 버전 증가 100회로 완료된다.
- 분야별 병렬 분석 비교 버튼·로직은 통합 분석 방향에 맞춰 제거한 상태다.

### 상태와 원자성

- 새 모드 이름: `single-session-pipeline-v1`.
- `batches.analysis.segments`에 원문 ID, 구간 상태, 분석 초안, 요약, 저장 결과·사용량을 기록한다.
- `lab_users.run_state`에 생성 예약과 단계별 진행 위치를 기록한다.
- 새 테이블·컬럼은 추가하지 않았다.
- 구간 상태는 `generated → analyzed → saved`다.
- 대화 추가와 구간 등록을 같은 트랜잭션으로 저장한다.
- 프로필·기억·구간 완료·진행 상태도 같은 저장 트랜잭션으로 반영한다.
- 사용자 행을 잠근 뒤 최신 JSON을 수정해 생성 작업이 분석 결과를 덮어쓰지 않게 한다.
- 전체 배치의 최종 `saved`는 모든 구간 저장이 완료된 뒤 설정한다.

### 중단·재개·실패

- 중단은 현재 시작한 작업을 마친 뒤 정지한다.
- 새 생성·분석·저장은 시작하지 않는다.
- 생성 결과, 분석 초안, 이미 시작한 저장 트랜잭션은 보존한다.
- 두 작업이 모두 정리된 뒤 `paused`로 전환한다.
- 실패 시 다른 작업도 새 작업을 시작하지 않고 진행 중 결과를 보존한다.
- 재개 시 생성 완료 구간은 재생성하지 않고, 분석 초안이 있으면 저장부터 진행한다.
- 서버 재시작 시 DB 체크포인트를 기준으로 복구한다.
- 기존 실행 모드는 기존 순서로 재개하며, 신규 실행만 새 파이프라인을 사용한다.
- 실행 중 또는 미완료 중단·실패 상태에서는 수동 생성·분석·저장을 차단한다.

## 7. Spring AI 전환

### 문제와 확인

프로젝트에 Spring AI 의존성이 있었지만 초기 Clone Lab은 Java HTTP 클라이언트로 직접 OpenAI를 호출했다. 의존성이 존재하는 것과 실제 호출 경로가 프레임워크를 사용하는 것은 다르다는 점을 확인했다.

### 현재 구조

| 역할 | 구현 |
| --- | --- |
| 생성·분석·요약·일반 대화 응답 | `ChatClient → OpenAiChatModel` |
| 임베딩 | `OpenAiEmbeddingModel`, 1536차원 |
| 클론 도구 대화 | `ChatClient → LabResponsesChatModel` |
| 기억 검색·프로필 조회 | Spring AI `ToolCallback` |
| HTTP 상태·재시도 | `LabAiTransport`의 RestClient 인터셉터 |

Spring AI 1.1.8과 Spring Boot 버전은 유지했다. 사용 중인 Spring AI 버전에 기본 Responses 모델이 없어 호환 `ChatModel` 어댑터를 두었다. 생성·분석 등은 Chat Completions를 사용하고, 클론 도구 대화는 Responses API의 추론 항목과 도구 호출 이력을 보존한다.

서비스는 기존 `LabAi` 계약을 사용한다. `OpenAiLabClient`는 기존 이름을 유지한 프레임워크 파사드이며 직접 HTTP 요청을 작성하는 역할에서 분리됐다.

### 모델 기본값

| 단계 | 모델 | 추론 강도 |
| --- | --- | --- |
| 인물·테스트 대화 생성 | `gpt-6.1-sol` | `low` |
| 분석 | `gpt-6.1-sol` | `medium` |
| 요약 | `gpt-6.1-sol` | `medium` |
| 답변 | `gpt-6.1-terra` | 미지정 |
| 임베딩 | `text-embedding-3-small` | 해당 없음 |
| 프로필 수치 병합 | 서버 계산 | LLM 호출 없음 |

기존 `LAB_*` 환경변수를 사용하며 모델을 자동 대체하지 않는다. 추론 강도 환경변수를 빈 값으로 두면 해당 파라미터를 생략한다.

### API 재시도

- 일시적 429, 5xx, 연결·타임아웃 오류는 최초 요청 외 최대 4회 재시도한다.
- `Retry-After`가 있으면 따르고, 없으면 1·2·4·8초와 작은 무작위 지연을 사용한다.
- 인증 오류, 잔액 부족, 일반 400, 잘못된 JSON, 분석 검증 실패는 자동 재시도하지 않는다.
- 대기는 중단 가능하며 DB 저장 전체를 반복하는 재시도가 아니다.
- Spring AI 내부 시도 횟수는 1회로 두어 재시도가 중첩되지 않게 했다.

## 8. 패키지와 코드 컨벤션

### 패키지 정리

```text

  controller/   REST API, HTML·자원 응답, 예외 응답
  service/      대화·분석·저장·자동 실행·AI 및 지원 코드
  dao/          DB 접근, MyBatis Mapper, UUID TypeHandler
```

소스 25개를 기준으로 controller 3개, dao 3개, service 19개다. 최초 이동 시에는 24개였으며 이후 pretty print 포맷터가 추가됐다. MyBatis 타입 핸들러 탐색 경로도 `com.example.everme.lab.dao`로 수정했다.

### 비교한 학습 프로젝트

- `C:\gen-ai-course\projects\spring-ai-1.1\ch10-rag\src\main\java\com\example\demo`
- `C:\gen-ai-course\projects\spring-ai-1.1\ch11-tool-calling-practice\src\main\java\com\example\demo`

### 반영한 작성 방식

- 2칸 들여쓰기, 명시적 import, 한 문장씩 줄바꿈.
- 지역 변수의 추론 타입을 명시적 타입으로 정리.
- 제어문 본문에 중괄호 적용.
- 필드·생성자·주요 메소드에 `// ##### ... #####` 구획 주석 추가.
- 컨트롤러의 축약된 필드명을 서비스 역할이 드러나는 이름으로 정리.
- ChatClient를 `prompt → system/user → options/advisors → call` 체인으로 작성.
- 운영 진단 로거는 Lombok `@Slf4j` 사용.
- 도구 메소드에 `@Tool`, 인자에 `@ToolParam` 적용.

- `MethodToolCallback`을 사용하되 기존 인자 검증·허용 순서·중복 실행 차단은 유지.

기존 생성자 주입과 controller/service/dao 구조를 유지했다. 예제의 자동 도구 실행을 그대로 복사해서 소유자 검증이나 단계 순서를 생략하지 않았다. 기존 작업 트리의 사용자 수정·문서 삭제 상태도 되돌리지 않았다.

## 9. LLM 로그와 한글 깨짐 트러블슈팅

### 직접 SLF4J 출력에서 Advisor로 전환

요청에 따라 LLM 요청·응답을 직접 기록하던 로그를 제거하고 두 ChatClient에 `SimpleLoggerAdvisor`를 등록했다.

```properties
logging.level.org.springframework.ai.chat.client.advisor.SimpleLoggerAdvisor=DEBUG
```

SimpleLoggerAdvisor 자체는 내부적으로 SLF4J를 사용한다. 변경의 의미는 애플리케이션 코드가 LLM 요청·응답을 직접 출력하는 대신 Spring AI Advisor에 맡긴다는 것이다. HTTP 재시도·서비스 처리 시간은 별도 운영 로그로 유지한다. 임베딩은 ChatClient Advisor 적용 대상이 아니며 벡터 본문을 출력하지 않는다.

### 증상: 한글이 `?뱀떊...`처럼 깨짐

확인한 사실:

- `LabService` 소스의 한글은 UTF-8로 정상 저장돼 있었다.
- 컴파일된 클래스에도 프롬프트의 한글 상수가 정상적으로 들어 있었다.
- 확인 당시 Windows 기본 인코딩은 CP949 계열이고 콘솔 출력 인코딩은 UTF-8이었다.

따라서 소스 손상보다는 출력 경로의 인코딩 불일치를 의심했다. 실행 중인 JVM의 모든 출력 경로를 직접 측정한 것은 아니므로 원인을 한 단계로 단정하지는 않는다.

반영:

- Gradle JavaCompile의 `options.encoding = 'UTF-8'`.
- JavaExec에 `file.encoding`, `stdout.encoding`, `stderr.encoding`을 UTF-8로 명시.
- `logging.charset.console=UTF-8`, `logging.charset.file=UTF-8`.
- 시작 PowerShell의 입력·출력 콘솔 인코딩과 `$OutputEncoding`을 UTF-8로 설정.
- 변경 후 기존 서버를 완전히 종료하고 재실행하도록 안내.

이후 공유된 로그에서 한글 프롬프트와 대화가 정상 표시되는 것을 확인했다. 이미 깨져 저장된 문자열이 있다면 출력 인코딩 변경만으로 복원되지는 않는다.

### 증상: 로그 전체가 긴 한 줄로 표시됨

기본 Advisor의 `ChatClientRequest.toString()` 출력은 중첩 객체와 JSON이 한 줄로 섞여 읽기 어려웠다.

`LabAiLogFormatter`를 추가하고 Advisor의 `requestToString`, `responseToString`을 설정했다.

```text
=== LLM REQUEST ===
--- CONTEXT ---
단계와 입력 크기
--- SYSTEM ---
프롬프트 원문
--- USER ---
들여쓰기된 입력 JSON
--- MODEL OPTIONS ---
모델·추론·JSON Schema 설정
=== END LLM REQUEST ===

=== LLM RESPONSE ===
--- ASSISTANT ---
응답 내용과 들여쓰기된 JSON
--- TOOL CALLS ---
도구 호출이 있을 때 표시
--- METADATA ---
사용량 등 메타데이터
=== END LLM RESPONSE ===
```

Responses 호출은 별도 `RESPONSES INPUT` 항목으로 원본 입력 이력을 표시한다. 프롬프트·대화 JSON·모델 요청 자체를 바꾸지 않고 로그 표현만 바꾼다. Windows JSON 출력의 CRLF와 구획의 LF가 섞이던 부분도 정규화했다.

Advisor 로그에는 사용자 대화와 분석 내용이 포함된다. API 인증 키는 Advisor 입력에 전달하지 않는다.

## 10. 화면 수치와 진행률 고민

- `NULL`과 초기 기준값 50을 화면에서 혼동하지 않도록 구분했다.
- 저장된 DB 값과 저장 전 관찰값을 가까운 위치의 이중 막대로 비교한다.
- 저장 전 분석 결과는 별도 색상으로 표시한다.
- 마지막 구간까지 저장되면 저장 전 미리보기 막대를 제거한다.
- 생성·분석·저장 쌍 수와 각 작업의 상태를 따로 표시한다.
- 전체 완료 진행률은 저장 완료 수를 기준으로 한다.
- 실제 활성 실행 시간 `wallElapsedMs`와 LLM 호출 시간 합계 `llmElapsedMs`를 구분한다.
- 병행 실행에서는 LLM 시간 합계가 실제 경과 시간보다 길 수 있다.
- 토큰 집계는 응답에서 확인 가능한 성공한 텍스트 호출 기준이며 임베딩·실패 요청을 포함한 청구 금액과 동일하지 않다.

## 12. 최근 기억·장기 기억·분석 프로필을 사용하는 방향

### 사용자가 원하는 방향 — 아직 미구현

1. turns에는 최근 100쌍의 대화만 유지한다.
2. 오래된 대화에서 장기 기억을 추출해 memories에 저장한다.
3. 장기 기억 저장이 완료된 뒤 해당 원문을 turns에서 삭제한다.
4. turns와 memories 모두 임베딩한다.
5. 사용자와 대화하는 AI에는 turns의 최근 대화를 컨텍스트로 제공한다.
6. 정보이용자 클론은 최근 기억을 먼저 검색하고, 부족하면 장기 기억을 검색하며, 성향·선택 판단에 분석 프로필을 활용한다.

대화에서 말한 “100개”는 우선 100쌍으로 해석해 논의했다. 실제 구현 전 사용자 발언 100개인지, 양쪽 메시지 합계 100개인지, 소유자 전체인지 세션별인지 범위를 확정해야 한다.

### 현재 코드와의 차이

| 항목 | 현재 구현 | 원하는 방향 |
| --- | --- | --- |
| 원문 보관 | turns에 계속 보관 | 최근 100쌍으로 제한 |
| turns 임베딩 | 없음 | 필요 |
| memories 임베딩 | 있음 | 유지 |
| 테스트 대화 생성 입력 | 주제·최근 4쌍 | 사용자 대화 컨텍스트 확대 검토 |
| 최근 기억 확인 | 선택한 저장 완료 배치 원문을 컨텍스트로 제공 | turns의 관련 기억 검색 |
| 장기 기억 | 분석 저장 시 추출·저장 | 오래된 원문 정리와 연계 |

사용자와 대화할 때 최근 이력을 시간순으로 전달하는 것은 컨텍스트 구성이고, 질문에 관련된 기억을 검색해 전달하는 것은 RAG다. 최근 100쌍 보관 정책과 실제 모델 입력 토큰 한도는 별도로 관리해야 한다.

### 후속 구현 때 함께 풀어야 할 문제

- 원문 삭제 후에도 기억·수치·답변의 출처를 추적할 방법.
- 이미 반영한 발언의 중복 분석 방지 기록 유지.
- 분석·장기 기억 저장 전에 원문을 삭제하지 않는 순서 보장.
- 고정 구간 원문 ID와 요약 캐시, 자동 실행 재개 정보의 정합성.
- 삭제 후에도 대화 순번과 1000쌍 진행 수가 초기화되지 않도록 절대 순번·처리 위치 관리.
- 최근 기억과 장기 기억의 검색 범위, 중복 결과 처리, 토큰 한도와 요약 정책.
- 프로필 점수를 과거 사건·인물·날짜의 사실 근거로 사용하지 않는 규칙 유지.

이 방향을 설명한 뒤 오늘 실제로 수행한 작업은 코드 컨벤션 정리다. 최근 100쌍 보관·이관 기능이 이미 적용됐다고 이해하면 안 된다.

- 변경 후 실제 생성 시간·분석 품질·비용·캐시 적중률의 개선 폭을 새로 측정하지 않았다.
- 140개 요소의 심리측정 타당성이나 실제 사람의 복제 정확도를 증명한 것은 아니다.
- 최근 100쌍 기억 이관·삭제·이중 임베딩 설계는 아직 구현·검증하지 않았다.

## 15. 다음 작업 후보

- 최근 100개 정책의 단위와 사용자별·세션별 범위를 확정한다.
- turns 임베딩과 최근 기억 검색, 장기 기억 이관·원문 삭제를 포함한 설계를 별도 계획으로 만든다.
- 원문 삭제와 분석 체크포인트·근거 추적·중복 반영 방지의 정합성을 먼저 정한다.
- 소량 실제 API 실험으로 생성 지연·관찰 근거 충실도·클론 답변의 사실성과 추정을 평가한다.
- 정리된 코드 컨벤션 변경사항을 검토 후 별도 커밋한다.
- 삭제된 설계 문서를 참조하는 링크와 오래된 문서 항목을 정리한다. 예를 들어 실행 README의 과거 병합 모델 환경변수 안내는 현재 서버 병합 구현과 구분해야 한다.
